# 토스 인앱 서비스 제품 발견 기록

- 작성일: 2026-08-11
- 단계: 문제 탐색
- 목표: 혼자 사용해도 첫날부터 가치가 생기는 토스 인앱 서비스 주제 발견
- 현재 선두 후보: 반복 통근자를 위한 환승 타이밍 에이전트

## 1. 창업자·개발자 성향

대화와 해커톤 작업 과정에서 확인한 성향은 다음과 같다.

- 실제로 움직이는 결과물을 빠르게 만들고 직접 사용하면서 판단한다.
- 기능보다 사용자가 느끼는 장면과 완성도를 중요하게 본다.
- 반복적인 입력·검색·정리처럼 결과를 얻기 전에 필요한 수고를 싫어한다.
- AI를 검색 도구가 아니라 기획·구현·검증을 함께 수행하는 작업자로 사용한다.
- 초기 사용자 수가 확보되어야 가치가 생기는 서비스보다 혼자서 즉시 검증 가능한 도구가 적합하다.
- 장점은 빠른 실행과 감각적인 판단이고, 위험은 검증 전에 범위를 확장하는 것이다.

## 2. 제품 선택 원칙

후보 서비스는 다음 조건으로 평가한다.

1. 다른 사용자가 없어도 혼자 사용할 수 있다.
2. 첫 사용 당일부터 명확한 효용이 있다.
3. 매일 또는 매주 반복해서 사용할 이유가 있다.
4. 사용자가 직접 입력해야 하는 정보가 적다.
5. AI 또는 자동화가 검색·기록·판단 중 하나를 대신한다.
6. 사용할수록 개인화 데이터가 쌓인다.
7. 네트워크 효과는 필수가 아니라 이후 확장 수단이어야 한다.

## 3. 탐색한 문제와 판단

### 3.1 비밀번호·비밀 메모

#### 관찰

- OAuth·SSO가 없는 사이트에서는 비밀번호를 기억하지 못해 비밀번호 찾기를 반복한다.
- 같은 비밀번호를 재사용하면 편하지만 보안 위험이 커진다.

#### 초기 아이디어

- 각 디바이스의 로컬 저장소를 이용한 개인 비밀 메모장
- 비밀번호 원문 대신 복구 힌트를 저장하는 금고
- 일회성 비밀 전달 도구

#### 판단

보류한다. 사용자가 회원가입 때마다 별도로 앱을 열어 저장해야 하면 기존 불편보다 입력 수고가 커진다. 충분히 편리하려면 브라우저·운영체제의 키체인처럼 가입 화면에서 자동으로 동작해야 하므로 토스 인앱에서 시작할 MVP 범위를 넘어갈 가능성이 높다. 보안과 초기 신뢰 장벽도 크다.

### 3.2 목적형 동네 친구 찾기

#### 관찰

- 의왕시는 사용자 밀도가 낮아 목적과 시간이 맞는 친구를 찾기 어렵다.
- 행정구역보다 실제 이동 가능한 생활권을 기준으로 연결하는 것이 현실적이다.
- 친구 관계를 먼저 요구하기보다 산책·식사·공부 같은 활동을 먼저 성사시키는 편이 부담이 적다.

#### 초기 아이디어

- 활동·시간·이동 가능 거리 기반 3~4인 자동 매칭
- 프로필 무한 탐색 대신 정해진 시간의 소규모 모임 생성

#### 판단

보류한다. 제품의 가치가 지역별 사용자 밀도에 직접 의존한다. 첫 지역의 콜드 스타트, 노쇼, 안전, 성비와 신뢰 문제를 해결해야 하므로 빠른 1인 개발·검증 방식과 맞지 않는다.

### 3.3 개인 기억 저장소

#### 관찰

- Obsidian, Apple 메모, 카카오톡 나에게 보내기 등 여러 저장소를 사용한다.
- 생각과 기록을 매번 별도 저장소에 공유하는 과정이 귀찮아 기록하지 않고 잊는 일이 많다.

#### 기회

- 저장 기능보다 캡처 과정의 마찰을 줄이는 것이 핵심이다.
- 링크·텍스트·음성을 2초 안에 넣고 AI가 자동 분류·요약·재노출하는 방식이 가능하다.

#### 위험

- 사용자가 앱을 따로 열어야 한다면 또 하나의 저장소가 된다.
- 외부 앱의 공유 기능이나 운영체제 수준 진입점이 없으면 핵심 문제를 해결하기 어렵다.

### 3.4 음악 청취 기록·자동 플레이리스트

#### 관찰

- 음악은 매일 듣지만 플레이리스트는 각 플랫폼에 종속된다.
- 좋아하는 노래를 매번 직접 저장하는 작업도 귀찮다.

#### 아이디어

- 실제 청취 횟수, 반복 재생, 스킵률을 이용해 곡을 자동으로 등급화한다.
- 일정 기간 많이 들은 상위 티어 곡을 자동 플레이리스트에 넣는다.
- 월별 취향 변화와 오래 듣지 않은 곡을 보여준다.

#### 위험

- 음악 플랫폼별 재생 기록·플레이리스트 API와 인증 정책에 크게 의존한다.
- 플랫폼 간 이동이 제한되면 또 하나의 보조 통계 앱에 머물 수 있다.

### 3.5 개인화 식단 추천

#### 관찰

- 식단을 진행하고 샐러디 같은 메뉴를 반복해서 먹는다.
- 개인 체형과 건강 목표에 어떤 메뉴·양·영양 구성이 맞는지 궁금할 수 있다.

#### 판단

우선순위를 낮춘다. 현재 사용자는 칼로리나 영양 정보를 자주 확인하지 않으며 이 문제 때문에 반복 행동을 하고 있지 않다. 호기심은 있으나 강한 실제 불편으로 확인되지 않았다.

## 4. 실제 출퇴근 사용자 여정

### 4.1 출근: 집 → 인덕원역 → 사당 → 회사

1. 집에서 네이버 지도 앱을 연다.
2. 현재 위치에서 인덕원역까지 경로를 검색한다.
3. 집 근처 정류장에 탈 버스가 몇 분 뒤 도착하는지 확인한다.
4. 남은 시간을 보고 정류장까지 달릴지 걸을지 판단한다.
5. 버스에서 내리기 전에 카카오지하철 앱을 연다.
6. 인덕원역에 전철이 몇 분 뒤 도착하는지 확인한다.
7. 전철을 잡기 위해 빠르게 내리고 횡단보도를 뛰어 건널지 판단한다.
8. 사당역 2호선은 배차가 잦아 별도 확인하지 않는다.

### 4.2 퇴근: 회사 → 사당 → 인덕원역 → 집

1. 사당에서 인덕원 방향 열차가 몇 분 뒤 도착하는지 확인한다.
2. 인덕원역 도착 전후 네이버 지도 앱을 연다.
3. 위치 기반 출발지가 잡힐 때까지 기다린다.
4. 목적지로 저장된 집을 선택하고 다음 교통편을 확인한다.
5. 남은 시간을 보고 이동 속도를 결정한다.

### 4.3 반복되는 핵심 판단

사용자가 원하는 것은 새로운 경로 추천이 아니라 다음 질문에 대한 즉각적인 답이다.

- 지금 뛰면 다음 교통편을 잡을 수 있는가?
- 뛰지 않고 걸어도 되는가?
- 이미 놓쳤으니 체력을 쓰지 않아도 되는가?
- 이번 교통편을 놓치면 최종 도착 시간이 몇 분 늦어지는가?

지도 앱과 지하철 앱은 사용자가 검색하면 원시 정보를 보여준다. 그러나 사용자는 버스 도착 시간과 도보 거리, 다음 전철 시간을 조합해 매번 직접 행동을 결정한다.

## 5. 현재 선두 가설: 환승 타이밍 에이전트

### 한 문장 정의

> 매일 같은 길을 오가는 사람에게 검색 없이 `뛰어야 함`, `걸어도 됨`, `다음 차가 나음`을 알려주는 반복 통근 전용 에이전트.

### 임시 서비스명

- `뛸까?`
- `지금갈까`
- `환승각`

`뛸까?`는 사용자가 실제로 해결하려는 질문을 그대로 표현한다는 장점이 있다.

### 예상 화면

```text
인덕원역 가는 버스

지금 뛰면 잡을 수 있어요
정류장까지 6분 · 버스 도착 8분

놓치면 다음 버스는 13분 뒤
예상 회사 도착 08:47 → 09:02
```

버스에서 인덕원역에 접근하면 다음 판단으로 자동 전환한다.

```text
인덕원역 전철

이번 열차는 빠르게 내리면 가능해요
전철 도착 5분 · 승강장까지 예상 4분

다음 열차와 차이 7분
```

### 기존 지도 앱과의 차이

- 모든 경로를 검색하는 범용 지도 앱이 아니다.
- 사용자가 저장한 반복 경로 몇 개만 매우 빠르게 판단한다.
- 도착 시간을 보여주는 데서 끝나지 않고 행동을 추천한다.
- 앱을 열어 검색하는 방식보다 적절한 순간에 먼저 알려주는 방향을 지향한다.

### 초기 MVP 가설

1. 집, 회사, 핵심 환승역과 평소 이용 경로를 한 번 저장한다.
2. 현재 정류장까지 예상 이동 시간과 버스 도착 시간을 합친다.
3. 여유 시간에 따라 `뛰기`, `빠르게 걷기`, `여유`, `다음 차`로 표시한다.
4. 교통편을 놓쳤을 때 최종 도착 시간 손실을 보여준다.
5. 출근·퇴근 시간에는 검색 없이 저장된 경로를 첫 화면에 노출한다.

## 6. 현재 후보 순위

| 순위 | 후보 | 이유 |
|---:|---|---|
| 1 | 환승 타이밍 에이전트 | 평일마다 반복되고 행동 결정과 시간 절약에 직접 연결됨 |
| 2 | 개인 기억 자동 저장소 | 불편은 크지만 저장 진입 마찰을 해결할 방법이 먼저 필요함 |
| 3 | 음악 청취 티어·자동 플레이리스트 | 사용 빈도는 높지만 외부 플랫폼 API 의존도가 큼 |
| 4 | 개인화 식단 추천 | 현재 사용자의 반복 행동이나 강한 불편으로 확인되지 않음 |

## 7. 검증이 필요한 가정

- 실시간 버스·지하철 도착 정보를 합법적이고 안정적으로 가져올 수 있는가?
- 토스 인앱에서 위치, 푸시 알림, 백그라운드 갱신을 어느 범위까지 사용할 수 있는가?
- 사용자는 처음 한 번의 통근 경로 등록을 감수할 만큼 반복 검색을 불편해하는가?
- 도보 예상 시간만으로 `뛸까 말까`를 충분히 정확하게 판단할 수 있는가?
- 놓쳤을 때의 시간 손실을 보여주는 것이 단순 도착 시간보다 더 큰 가치가 있는가?

## 8. 다음 인터뷰 질문

1. 출근 중 버스와 전철을 놓쳤을 때 실제 손실 시간은 각각 얼마나 되는가?
2. `뛰어야 함` 알림을 받으려면 사용자가 앱을 직접 여는 것만으로 충분한가, 아니면 푸시 알림이 반드시 필요한가?
3. 매일 타는 버스 번호와 전철 노선은 거의 고정되어 있는가?
4. 사용자는 빠른 교통편보다 덜 뛰고 덜 스트레스받는 선택을 원할 때도 있는가?
5. 단순 도착 시간보다 `이 교통편을 놓치면 최종적으로 몇 분 늦는다`가 더 중요한가?

# 개발자 기회 캘린더 제품 기획서

- 작성일: 2026-08-11
- 문서 상태: 1차 가설
- 개발 환경: 앱인토스 미니앱
- 임시 서비스명: `기회 캘린더`
- 첫 시장: 기술 행사·해커톤 기회를 찾는 수도권 개발자와 개발 직군 준비생

## 1. 제품 요약

### 한 문장 정의

> 관심 기술과 참여 조건을 선택하면, 나에게 맞는 컨퍼런스·밋업·해커톤을 신청 마감 전에 알려주는 개발자 기회 캘린더.

### 장기 비전

사용자가 관심사를 선택하면 쇼핑, 전시, 공연, 컨퍼런스, 채용행사처럼 `지금 알지 못하면 놓칠 수 있는 기회`를 자동으로 발견하고 적절한 시점에 행동하도록 돕는다.

### 첫 제품 범위

장기 비전을 한 번에 구현하지 않는다. 첫 제품은 개발자가 배우고, 만들고, 사람을 만날 수 있는 기회만 다룬다.

- 사용자: 최근 6개월 안에 기술 행사나 해커톤을 찾아보거나 참여하려 한 수도권 개발자·개발 직군 준비생
- 관심사: AI, 백엔드, 프론트엔드, 모바일, 클라우드, 기술 일반
- 기회: 컨퍼런스, 밋업, 워크숍, 해커톤, 개발 공모전
- 지역: 서울, 경기, 온라인
- 핵심 행동: 기회 발견 → 저장 → 마감 알림 → 신청 페이지 이동

## 2. 배경과 문제

### 사용자 관찰

개발자는 컨퍼런스, 밋업, 해커톤에 관심이 있어도 정보를 꾸준히 찾아보기 어렵다. 정보가 다음과 같은 채널에 흩어져 있기 때문이다.

- 주최 기업과 기술 커뮤니티 홈페이지
- Meetup, Event-us, Festa, Luma 등 행사 플랫폼
- GitHub 저장소와 개발 커뮤니티
- 해커톤·공모전 모집 플랫폼과 대학·기관 공지
- LinkedIn, Instagram, X 등 소셜 미디어
- 회사 동료와 단체 채팅방
- 개별 뉴스레터

사용자는 모든 채널을 상시 확인하지 않는다. 그 결과 관심 있는 행사를 신청 마감 후 발견하거나, 접수 시작 사실을 늦게 알고 정원이 찬 뒤에 확인한다.

### 핵심 문제

> 사용자는 자신에게 맞는 개발자 기회가 어디에 올라오는지 모두 알 수 없고, 알게 되더라도 신청 가능한 시기를 놓친다.

### 기존 대안과 한계

| 기존 대안 | 장점 | 한계 |
|---|---|---|
| 일반 캘린더 | 익숙하고 알림을 설정할 수 있음 | 사용자가 행사를 먼저 알고 직접 입력해야 함 |
| 행사 플랫폼 | 해당 플랫폼의 행사 탐색에 유리함 | 여러 플랫폼과 주최자 사이트에 정보가 분산됨 |
| 개발 커뮤니티 | 관심 분야 정보의 질이 높음 | 중요한 공지가 다른 대화에 묻히고 상시 확인이 필요함 |
| `Dev Event` | 개발자 행사를 한곳에 큐레이션함 | 개인화된 마감 알림과 앱인토스 기반 재방문 경험은 추가 검증 필요 |
| 주최자 알림 | 정보가 정확함 | 이미 알고 팔로우한 주최자의 행사만 발견 가능 |

## 3. 제품 가설

### 핵심 가치 가설

사용자가 기술 관심사, 참여 목적, 참가 자격, 이동 가능 지역을 한 번 설정하면 직접 여러 채널을 검색하지 않아도 참여할 만한 기회를 발견할 수 있다.

### 행동 가설

- 사용자는 자신과 관련성이 높은 행사라면 토스 안에서 저장한다.
- 사용자는 일반적인 신규 행사 알림보다 `신청 시작`, `마감 임박` 알림에 더 강하게 반응한다.
- 사용자는 매일 앱을 탐색하지 않더라도 주간 추천과 마감 알림을 통해 다시 방문한다.
- 저장한 행사의 신청 페이지로 바로 이동할 수 있으면 실제 신청 가능성이 높아진다.

### 사업 가설

- 초기에는 사용자 가치를 우선 검증하고 무료로 제공한다.
- 사용자와 저장 데이터가 쌓이면 행사 주최자 대상 추천 노출, 스폰서 행사, 제휴 신청 전환으로 수익화할 수 있다.
- 광고성 행사와 일반 추천을 명확히 구분해야 신뢰를 유지할 수 있다.

## 4. 목표 사용자

### 1차 핵심 사용자 가설

`최근 6개월 안에 기술 행사나 해커톤을 찾아본 적이 있고, 여러 모집 채널을 매일 확인하지 않아 신청 기회를 놓친 수도권 개발자·개발 직군 준비생`

직업명이나 연차보다 실제 탐색 행동과 놓친 경험으로 사용자를 정의한다. 온보딩에서는 현직자·취업준비생·학생을 구분해 추천 조건으로 활용하되, 서비스 진입 자격으로 제한하지 않는다.

#### 특성

- 관심 기술 분야가 한두 개 이상 분명하다.
- 분기당 한 번 이상 컨퍼런스·밋업·해커톤에 참여할 의향이 있다.
- 평일 저녁이나 주말에 수도권 행사에 참석할 수 있다.
- 행사 정보를 동료, 커뮤니티, 소셜 미디어에서 우연히 발견한다.
- 관심 있는 행사나 해커톤을 뒤늦게 발견한 경험이 있다.
- 행사 탐색을 위해 새로운 독립 앱을 설치하는 것은 부담스러워한다.

### 후속 확장 사용자

- 시니어 개발자와 리더: 전문 컨퍼런스, 네트워킹, 리더십 행사
- 기획자와 디자이너: 제품, UX, 디자인 행사
- 일반 사용자: 전시, 공연, 팝업, 한정판 상품 발매

### 초기 제외 사용자

- 일반 채용공고만 찾는 사용자
- 수도권 외 오프라인 행사만 원하는 사용자
- 쇼핑, 공연, 전시 일정만 원하는 사용자
- 교육 상품과 자격증 과정을 비교·구매하려는 사용자

## 5. 사용자의 해야 할 일(JTBD)

### 기능적 과업

> 내 관심 분야에서 배우고, 만들고, 사람을 만날 기회를 찾고, 신청할 수 있을 때 놓치지 않고 신청하고 싶다.

### 감정적 과업

> 좋은 행사를 뒤늦게 발견했을 때 생기는 아쉬움과 정보 탐색 피로를 줄이고 싶다.

### 사회적 과업

> 업계 흐름을 놓치지 않고 배우고 교류하는 개발자로 성장하고 싶다.

## 6. 가치 제안

### 사용자에게 제공하는 가치

1. 여러 채널에 흩어진 개발자 기회를 한곳에서 발견한다.
2. 전체 인기순이 아니라 나와 관련성이 높은 순서로 본다.
3. 행사 날짜보다 신청 시작일과 마감일을 중심으로 관리한다.
4. 놓치기 쉬운 순간에 토스 푸시를 받는다.
5. 알림을 누르면 원래 신청 페이지로 바로 이동한다.

### 핵심 차별점

> 새로운 행사를 많이 보여주는 것이 아니라, 나에게 맞고 곧 놓칠 행사를 먼저 보여준다.

## 7. 정보 구조

### 하단 메뉴 가설

1. `추천`: 이번 주 신청 시작·마감 기회
2. `캘린더`: 월별 행사·해커톤 신청 일정
3. `저장`: 내가 저장하고 알림을 설정한 기회
4. `내 관심사`: 기술, 지역, 비용, 시간대 설정

### 첫 화면 원칙

달력보다 `이번 주 놓치면 끝나요` 목록을 먼저 보여준다. 달력은 날짜 탐색을 위한 보조 화면으로 사용한다.

```text
이번 주 놓치면 끝나요

D-1  AI 에이전트 밋업
     무료 · 서울 강남 · 목요일 저녁

D-3  클라우드 아키텍처 워크숍
     유료 · 온라인 · 토요일

오늘 접수 시작

19:00  백엔드 개발자 네트워킹
       무료 · 서울 성수
```

## 8. 핵심 사용자 흐름

### 8.1 첫 이용

1. 사용자가 미니앱을 연다.
2. 관심 기술을 선택한다.
3. 선호 기회 유형과 참여 목적을 선택한다.
4. 이동 가능 지역과 온라인 참여 여부를 선택한다.
5. 무료·유료, 평일 저녁·주말 선호를 선택한다.
6. 조건에 맞는 추천 행사 목록을 즉시 확인한다.
7. 관심 행사 하나를 저장하고 알림에 동의한다.

### 8.2 행사 발견과 저장

1. 추천 화면에서 행사 카드와 마감 상태를 확인한다.
2. 상세 화면에서 행사 내용과 출처를 확인한다.
3. `저장하고 알림받기`를 누른다.
4. 기본 알림 시점을 확인하거나 수정한다.

### 8.3 마감 알림과 신청

1. 신청 시작 또는 마감 전에 토스 푸시를 받는다.
2. 푸시를 누르면 행사 상세 화면으로 이동한다.
3. `신청하러 가기`를 누른다.
4. 외부 공식 신청 페이지가 열린다.
5. 사용자가 신청 완료 여부를 선택적으로 기록한다.

## 10. 개인화와 정렬

### 입력 신호

- 선택한 기술 분야
- 기회 유형
- 참여 목적: 학습, 네트워킹, 포트폴리오, 수상, 커리어
- 현재 상태: 현직자, 취업준비생, 학생
- 지역과 온라인 여부
- 무료·유료 선호
- 참여 가능한 요일과 시간대
- 행사 저장, 숨김, 신청 페이지 이동 기록

### 추천 우선순위

1. 사용자 관심사와의 관련성
2. 신청 마감까지 남은 시간
3. 사용자의 참석 가능 지역·시간
4. 출처의 신뢰도와 정보 완성도
5. 다른 사용자의 저장 증가량

인기만 높은 행사가 모든 사용자에게 노출되지 않도록 관련성과 참석 가능성을 먼저 고려한다.

## 11. 알림 정책

### 저장한 행사

- 신청 시작 시점
- 신청 마감 3일 전
- 신청 마감 당일
- 행사 하루 전

사용자는 행사별로 원하는 알림만 선택할 수 있다.

### 저장하지 않은 추천 행사

- 주 1회 개인화 추천 모음
- 관련성이 매우 높은 행사에 한해 마감 임박 알림

추천 알림을 과도하게 보내지 않는다. 사용자에게 알림 빈도와 관심 분야를 직접 조절할 수 있는 수단을 제공한다.

## 12. 데이터 수집 전략

### 원칙

`웹 전체 자동 크롤링`을 목표로 삼지 않는다. 허용되고 신뢰할 수 있는 데이터원을 넓히면서 유용한 범위를 만든다.

### 데이터원 우선순위

1. 공식 Open API
2. 행사 주최자의 RSS, ICS, JSON-LD 등 구조화 데이터
3. 수집이 허용된 공식 공개 페이지
4. 행사 주최자 직접 등록
5. 사용자 링크 제보
6. 운영자 수동 등록

### 처리 흐름

```text
데이터 수집
→ AI 정보 추출
→ 표준 행사 형식으로 변환
→ 중복 탐지
→ 출처·날짜 검증
→ 자동 또는 수동 승인
→ 사용자에게 노출
→ 알림 전 원문 재확인
```

### 신뢰도 등급

| 등급 | 데이터원 | 게시 방식 |
|---|---|---|
| A | 공공 API, 공식 주최자 피드 | 자동 게시 |
| B | 검증된 사이트의 구조화 페이지 | 자동 게시 후 주기적 재확인 |
| C | 일반 웹페이지, 사용자 제보 | AI 추출 후 운영자 검수 |
| D | SNS 이미지, 로그인 필요 페이지 | 수동 등록·확인 |

### 법률·정책 원칙

- 사이트별 이용약관과 `robots.txt`를 확인한다.
- 로그인, CAPTCHA, 접근 제한을 우회하지 않는다.
- 설명과 이미지를 통째로 복제하지 않는다.
- 행사명, 날짜, 장소 같은 최소 사실 정보와 원문 링크를 중심으로 제공한다.
- 특정 서비스의 데이터베이스를 반복적·체계적으로 복제하지 않는다.
- 외부 프로젝트와 공개 저장소 데이터는 라이선스와 사용 정책을 확인한 뒤 사용한다.

## 13. 운영자 도구

소비자 화면과 별개로 데이터 품질을 위한 최소 운영 화면이 필요하다.

- 수집된 행사 후보 목록
- AI 추출 결과와 원문 비교
- 승인, 수정, 거절
- 중복 행사 병합
- 일정 변경·취소 처리
- 출처별 오류 현황
- 사용자 오류 신고 확인

MVP에서는 완전 자동화보다 한 명이 하루 10~20개 후보를 빠르게 검수할 수 있는 운영 효율을 목표로 한다.

- 개인화 추천 목록
- 마감 중심 기회 카드
- 월간 캘린더
- 행사 상세와 공식 출처
- 해커톤의 참가 자격·팀 구성·제출 마감 정보
- 행사 저장
- 토스 알림 수신 동의와 마감 알림
- 공식 신청 페이지 이동
- 기본 운영자 검수 화면

### MVP에서 제외

- 쇼핑, 전시, 공연 일정
- 일반 채용공고
- 결제와 티켓 구매
- 자동 예약·자동 구매
- 잔여 좌석·재고 예측
- 모든 웹사이트의 자동 크롤링
- 사용자 간 커뮤니티
- 행사 후기와 동행자 매칭
- 해커톤 팀원 매칭과 팀 관리
- 주최자 광고 상품

## 15. 경쟁과 포지셔닝

### 직접 경쟁

- 개발자 행사 큐레이션 서비스
- 행사 플랫폼의 개발 카테고리
- 커뮤니티 행사 게시판

### 간접 경쟁

- Google·Apple 캘린더

- 주최자 뉴스레터
- 동료 추천

### 초기 포지셔닝

> 개발자 행사를 많이 모은 목록이 아니라, 내 관심사에 맞고 곧 신청이 끝나는 컨퍼런스·밋업·해커톤을 토스에서 먼저 알려주는 서비스.

## 16. 성공 지표

### 북극성 지표 후보

`월간 유효 기회 연결 수`

추천 또는 알림을 통해 사용자가 공식 신청 페이지까지 이동한 횟수로 정의한다.

### 활성화 지표

- 온보딩 완료율
- 첫 방문에서 행사 한 개 이상 저장한 사용자 비율
- 알림 수신 동의율

### 가치 지표

- 추천 행사 저장률
- 행사 상세 → 신청 페이지 이동률
- 마감 알림 클릭률
- 사용자가 `신청했어요`로 기록한 비율

### 유지 지표

- 4주 이내 재방문율
- 월간 저장 사용자 수
- 주간 추천 알림 이후 재방문율

### 데이터 품질 지표

- 잘못된 날짜·장소 신고율
- 취소·변경 반영 시간
- 중복 행사 비율
- 출처별 수집 성공률

## 17. 주요 위험과 대응

| 위험 | 영향 | 초기 대응 |
|---|---|---|
| 행사 데이터 부족 | 추천 화면이 비어 보임 | 첫 분야와 지역을 좁히고 수동 큐레이션 병행 |
| 데이터 오류 | 알림 신뢰 상실 | 출처와 마지막 확인 시각 표시, 알림 전 재확인 |
| 기존 서비스와 차별성 부족 | 사용 이유가 약함 | 개인화와 마감 알림을 핵심 경험으로 검증 |
| 낮은 사용 빈도 | 리텐션이 낮음 | 주간 추천과 신청 시작·마감 순간을 재방문 계기로 설계 |
| 알림 피로 | 알림 해제와 이탈 | 저장 행사 중심, 빈도 설정, 추천 알림 제한 |
| 크롤링 차단·법적 위험 | 데이터 공급 중단 | API·제휴·직접 등록 우선, 출처별 정책 관리 |
| 운영 부담 증가 | 1인 개발 지속 불가 | 신뢰도 기반 자동 승인과 중복 제거 자동화 |
| 광고성 행사 범람 | 추천 신뢰 하락 | 교육 상품·스폰서 표시와 추천 기준 공개 |

## 18. 검증 계획

### 1단계: 문제 인터뷰

현직 개발자·취업준비생·학생을 포함해 15명 이상에게 다음을 확인한다. 단, 결과는 사용자 유형별로 분리해 비교한다.

1. 최근 6개월간 뒤늦게 발견해 놓친 행사나 해커톤이 있는가?
2. 평소 행사 정보를 어디서 발견하는가?
3. 행사 선택에 기술 분야, 지역, 비용, 시간 중 무엇이 가장 중요한가?
4. 어떤 알림 시점이 실제 신청 행동에 도움이 되는가?
5. 행사 추천을 받기 위해 토스 알림에 동의할 의향이 있는가?
6. 해커톤에서는 참가 자격, 팀 구성, 신청 마감, 제출 마감 중 어떤 정보가 가장 중요한가?

### 2단계: 수동 큐레이션 실험

전체 제품을 개발하기 전에 2주 동안 수동으로 실험한다.

- 행사 50~100개를 직접 정리한다.
- 참여자 20~30명의 관심사를 받는다.
- 개인별 주간 추천과 마감 알림을 제공한다.
- 저장 의향, 신청 페이지 클릭, 실제 신청 여부를 기록한다.

### 3단계: 데이터 수집 실험

- 우선 데이터원 20~30개를 선정한다.
- 구조화 데이터 추출 성공률을 측정한다.
- 중복과 일정 오류를 확인한다.
- 한 명이 하루에 검수해야 하는 후보 수와 시간을 측정한다.

### MVP 진행 조건

다음 신호가 확인되면 앱인토스 MVP 개발을 진행한다.

- 인터뷰에서 실제 행사 누락 경험이 반복적으로 발견된다.
- 추천받은 사용자가 행사 저장과 신청 페이지 이동 행동을 보인다.
- 제한된 데이터원으로도 매주 충분한 추천 후보를 공급할 수 있다.
- 운영자가 감당 가능한 수준으로 데이터 검수가 가능하다.

## 19. 열린 질문

### 사용자

- 현직 개발자·취업준비생·학생 중 누가 가장 자주 기회를 찾고 놓치는가?
- 직업·연차보다 `최근 탐색 경험`과 `놓친 경험`이 더 강한 사용자 구분 기준인가?
- 해커톤 참가자는 기존 기술 행사 사용자와 같은 추천·알림 경험을 원하는가?
- 수도권 오프라인 행사와 온라인 행사의 수요 차이는 어느 정도인가?

### 제품

- 첫 화면은 추천 피드와 캘린더 중 무엇이 더 자주 사용되는가?
- 저장하지 않은 행사도 마감 알림을 보내야 하는가?
- 사용자가 실제 신청 완료 여부를 기록할 동기가 있는가?
- `관심 급상승`이 행사 선택에 도움이 되는가?

### 데이터

- 첫 데이터원 20~30개는 어디인가?
- 외부 행사 큐레이션 프로젝트와 제휴 또는 합법적 연동이 가능한가?
- 일정 변경과 취소를 얼마나 빠르게 탐지할 수 있는가?
- 주최자가 직접 등록하게 만드는 가장 작은 보상은 무엇인가?

### 사업

- 주최자 추천 노출이 사용자 신뢰를 해치지 않도록 어떻게 구분할 것인가?
- 신청 전환 수수료, 광고, 주최자용 도구 중 어떤 모델이 가장 자연스러운가?
- 개발자 행사에서 일반 관심사로 확장할 시점은 언제인가?
